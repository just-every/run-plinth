# Shared company agent door

Use `/mcp` to discover the Construction project coordinator tool schemas, current scopes and policy revision. This installation declares tools, policy, pause, audit and idempotency. Prompts, public resources, events and subscriptions are undeclared and return typed refusals. The shared `/agents` person door provides policy, audit, reviews, approvals and Pause. Native owner/admin sessions remain responsible for final business decisions. Local bearer credentials keep their existing draft scope. See [the agent door guide](AGENT-DOOR.md).

The HTTP examples below describe the native draft payloads and the versioned SDK connector. Agent callers use those payloads inside each discovered MCP tool's `input`, with `job_id` and a stable `idempotency_key`. The installed Worker challenges unversioned bearer API requests with the MCP resource metadata.

# Draft preparation for agents

MCP is the agent command surface; the HTTP examples document the native payloads its supported tools use. Every call uses native authenticated authority, and every edit supplies the job's current `expected_version`. Read `plinth.jobs.get` before preparing a draft; a stale version returns 409 with no write. Integer amounts are cents. An agent credential can read manager-visible jobs and prepare drafts; it cannot create jobs, approve, issue, receive, export, import or erase.

A signed-in owner first completes Base's credential step-up (`POST /auth/step-up`, body `{"action":"credentials:mint","returnTo":"/app"}`), follows the ordinary email confirmation, then calls `POST /api/plinth/agent-credentials` with `{"expires_in_seconds":3600}` and a same-origin session. Its `credential.token` is shown once. Store it privately; send it as `Authorization: Bearer …`, never in a URL. `GET /api/plinth/agent-credentials` lists metadata; `POST /api/plinth/agent-credentials/:id/revoke` revokes one immediately. Suspension, role changes and expired or revoked native credentials remove access.

| Command (POST relative to `/api/plinth/jobs/:id`) | Draft input in addition to `expected_version` | Person's next step |
| --- | --- | --- |
| `/quotes` | `lines:[{description,quantity,unit_cents}], notes?` | Builder records actual client agreement in Quote, `/quotes/:id/accept` with `method` and `evidence` |
| `/schedules` | `trade,start,end,description` (ISO timestamps) | Builder approves the trade booking, `/schedules/:id/approve` |
| `/diary` | `date,note,attachments?:[{name,mime,base64}]` | Builder publishes the daily log, `/diary/:id/approve` |
| `/variations` | `description,amount_cents` (a change order) | Matching signed-in client approves the change order, `/variations/:id/approve` |
| `/orders` | `supplier,description,amount_cents` | Builder issues `/orders/:id/issue` |
| `/claims` | `description,cumulative_cents` (a pay app) | Builder reviews and approves the pay app, `/claims/:id/approve`, then records `/claims/:id/export` |

Dates use `YYYY-MM-DD`. Photos are PNG or JPEG, five maximum per entry and 2 MB each. Quantities are whole positive numbers. Negative change-order cents are allowed as credits when they do not reduce the contract below amounts already approved for billing.

Managers using a human session publish their own trade bookings and daily logs directly; agent-prepared versions wait for explicit approval. Approval history records preparer, approver, time and the exact snapshot. A client only sees published job records for their own email. Every mutation and file retrieval checks authority on the server, independently of the screen.

Purchase receipts use `/orders/:id/receive` with `amount_cents` and `reference`. Pay-app exports return an immutable `report`; repeating export returns the same report with no new approval or economic effect. The UI downloads CSV and full JSON. No provider is contacted by these product commands.

## Calendar subscriptions (INT-006)

A signed-in person opens a job's Schedule and creates a private calendar link, then pastes it into their calendar client's subscription field. It contains approved trade names, work descriptions and dates for that job only. Treat the URL as a credential. Rotation invalidates the previous URL; revoke removes access. Current account/job grants are checked on every fetch, and restoring a private archive requires a new link.

`POST /api/plinth/jobs/:id/calendar` with `expected_version` and `action: "rotate"` returns `urlPath` once; `action: "revoke"` revokes your subscription. Owners/admins and the assigned client manage their own link; bearer agents cannot. The URL serves read-only RFC 5545 iCalendar, with UTC instants, stable UIDs, incrementing sequences and cancellation tombstones. It contains no internal financial fields. A manager moves booked work through `/schedules/:id/move` with explicit-offset `start`/`end`, or cancels through `/schedules/:id/cancel`; both require `expected_version` and retain the previous decision in History. Moving still checks cross-job conflicts.

## Reusable customers and sites (CRM-001)

Owners and project managers use **Customers** to maintain household, business or person records, contacts, billing/owner roles, property addresses and contact history notes. In Jobs, **Use an existing customer and property** fills the site from its reusable record. The job's **Customer** tab shows current billing contacts and lets a manager change authorized contacts. Each authorized email receives the existing client-safe job access, including photos, change decisions and its own calendar feed. The original client email remains authorized. Removing an additional contact closes its access on the next request. Clients cannot browse the customer directory.

`GET/POST /api/plinth/customers` lists or creates customers; `GET/POST /api/plinth/customers/:id` reads or edits one. Records have `kind` (`household`, `person`, `business`), `name`, `external_id`, `owner_contact_ids` and `billing_contact_ids`. `POST /customers/:id/contacts` adds a contact (`name`, `email`, `phone`, `preferences`, `external_id`), and `/contacts/:contactId` edits it. `/contacts/:contactId/notes` appends an attributed `note`. `/properties` adds a `label` and `address`, and `/properties/:propertyId` edits them. Every edit supplies the current customer `expected_version`; stale writes fail atomically.

A job create or `POST /api/plinth/jobs/:id/customer` accepts `customer_id`, `property_id`, `client_contact_ids` and the job's `expected_version` for edits. `GET /jobs/:id/customer` returns the linked customer to managers. A new property link copies its address; later edits to that property preserve the existing job's site snapshot and the customer's before/after history. Directory records and job links travel in private archives; calendar credentials do not.

## Coded USD payment applications (BILL-001)

In an accepted job, open Billing and record its schedule of values. The quote and every approved change need retained reviewed pricing/tax snapshots; the priced-change form previews the same ordered EST-003 calculator and then waits for the client’s exact decision. Cost codes stay with their original source rows. New approved changes append in a later SOV revision.

For each application, enter cumulative completed work and materials still stored, plus dated source evidence. Stored materials refer to issued PO receipts; the same receipt money cannot fund two rows. Approval reserves the cumulative position. Issue freezes a commercial application with JSON, CSV and printable continuation sheet downloads, not a tax invoice or licensed AIA form. Reclassification from stored to completed does not bill twice.

The native HTTP doors are `POST /api/plinth/jobs/:id/sov` (`code_assignments` keyed by `quote:<line-id>` or `variation:<change-id>`); `POST .../variation-pricing/preview` and `.../apply` (fresh digest required); `POST .../claims` with all current `lines` (`line_id`, `completed_cents`, `stored_cents`, `evidence`, `order_ids`); then the existing `.../claims/:id/approve` and `.../claims/:id/issue`. Issued records download through `GET .../claims/:id/application.json`, `.csv` and `.html`. Every mutation includes `expected_version` and the native matching-origin session; bearer agents only preview and prepare application drafts. Earlier cumulative-only approvals cannot acquire invented coded or tax history.

## Component warranties and recurring maintenance (CARE-003)

Open a job’s Warranty section to record immutable signed terms and dates, an agreed maintenance schedule, defects, callback cost sources and coverage reviews. The named reviewer supplies the reason and exact source; this records human judgment rather than certifying legal coverage. Closing a case preserves its warranty and history.

`POST /api/plinth/jobs/:id/warranties` creates a `component`, `promise` or `case` using `kind`; `POST .../warranties/:recordId/:action` records `pause`, `resume`, `revoke`, `cost`, `review` or `close`. Every mutation carries `expected_version` and the native matching-origin session. The UI labels all required fields. `POST .../warranty-reminders/run` dispatches due occurrences for that job under live office authority; request data cannot override the clock. The hourly Worker trigger uses the same dispatcher with bounded pages and a private durable cursor.

Email requires the installation’s configured Base mail provider. Provider acceptance does not prove delivery. Each occurrence has one durable attempt; uncertain outcomes are never resent. Monthly/yearly dates preserve the original anchor with end-of-month clamping. Pause or revoke stops future sends; resuming requires a new agreement reference and current grants. Restored agreements remain inactive until explicitly reconfirmed under the receiving installation’s authority.

## Client retainage (BILL-003)

In Billing, open **Client retainage** after recording the SOV and before approving the first application. Record the signed contract reference, work/stored percentages per line and the contract's required completion/waiver references for substantial and final completion. Each later application freezes its calculated withholding alongside gross progress; supplier commitments and payments stay separate. After an approved draw, release part of its held amount at the configured substantial-completion milestone. At final completion release the remainder with the required final waiver reference. Evidence records a human review, not app verification of the underlying document or funds.

`POST /api/plinth/jobs/:id/retainage` accepts `contract_reference`, `rules:[{line_id,work_bps,stored_bps}]` and `milestones:[{id,name,completion_requirements:[],waiver_requirements:[],final?:boolean}]`. Rates are integer basis points; each work/stored calculation rounds half up separately to cents. Existing terms cannot change; submit the complete plan plus new rules/milestones to append terms for new approved SOV lines. `POST .../retainage/release` accepts `claim_id`, `milestone_id`, `lines:[{line_id,amount_cents}]`, `completion_reference` and (for final release) `waiver_reference`, plus `completion_references` and `waiver_references` arrays of `{requirement,reference}` matching every configured requirement. A provided required reference can supply the general completion/waiver reference. Every write uses the current `expected_version` and native matching-origin session. Bearer agents cannot approve terms or releases.

Manager job responses expose `retainage_balance` with the latest gross, prior/current/cumulative withheld, released, held and net payable; releases are not customer payments. Issued JSON, CSV and printable applications retain their original snapshots even after a release. Private archives retain terms and evidence with the job.

Supplier retainage is independent. On an awarded/released subcontract, office owners/admins use `POST /api/plinth/jobs/:id/subcontracts/:subId/retainage` before its first gross draw with `contract_reference`, `rate_bps` and the same `milestones` shape. `POST .../retainage/release` takes latest `draw_id`, a configured `milestone_id`, per-draw `lines:[{draw_id,amount_cents}]` and the same completion/waiver references. Supplier balances and original release sources appear separately in Billing and private archives. Client releases do not change them. Existing supplier payment records remain full-gross only: release that draw's held value first; net payment handoff is carried by PAY-003. No release itself records funds.

## Deposits and milestone invoices (BILL-002)

Billing shows **Invoices and deposits**, a separate deposit-liability/revenue breakdown, invoice decisions and a preparation form. A deposit request earns no construction revenue. Record externally received bank/check funds only after checking their source evidence; Plinth does not move or independently verify money. Prepare a milestone from an issued coded SOV application, issue its immutable invoice and apply part of a received deposit. The remaining liability stays available for later invoices. Retainage release changes the live source-invoice payable once while its original issue stays fixed.

`POST /api/plinth/jobs/:id/invoices` accepts `kind` (`deposit` or `milestone`), `description`, `recipient_email`, `due_on` and `terms`, plus `amount_cents` for a deposit or `source_application_id` for a milestone. `POST .../invoices/:invoiceId/issue` allocates the next installation-wide number. All writes use `expected_version`. `.../receipt` takes `amount_cents`, `received_on`, `reference`, `method` (`bank` or `check`) and `confirm:true`; `.../apply-deposit` takes `deposit_invoice_id` and `amount_cents`. A currently assigned signed-in client uses `.../accept` with `statement` and `confirm:true`. Bearer agents only prepare drafts. Original artifacts download from `.../document.json`, `.csv` or `.html` under current grants.

`.../send` with `confirm:true` approves one durable email attempt to the currently authorized invoice contact through configured Base mail. Acceptance by the mail provider is delivery unconfirmed; development suppression, unconfigured mail, refusal and unknown outcomes remain visible. Email, client acknowledgment and recorded funds are separate facts. Original/current budgets, approved changes and human-reviewed tax sources remain with each issue; no provider tax verification or legal certification is claimed.


## Recorded remittances and current receivables (BILL-006, partial)

These native HTTP doors use the same signed-in owner, administrator or assigned project-manager authority as recording an invoice receipt. Every POST needs a matching Origin, `Content-Type: application/json` and the current job `expected_version`; bearer agents cannot record or return funds. They do not move or independently verify money, reconcile a provider or send a receipt.

- `POST /api/plinth/jobs/:job/remittances`: `amount_cents` (positive integer USD cents), `received_on` (job-local YYYY-MM-DD), `method` (`bank` or `check`, including a staff-recorded ACH bank posting), `reference`, `evidence`, `confirm: true`, and `allocations` (up to 200 unique `{invoice_id, amount_cents}` entries). Allocate only to issued milestone invoices on this job and no more than their current due balances. The receipt reference is unique on the job, including old single-invoice receipts and returned remittances. An empty list retains the full receipt as unapplied cash. Overpayments stay separate from deposit liability.
- `POST /api/plinth/jobs/:job/remittances/:id/allocate`: `applied_on`, `allocations` and `confirm: true` consume only the remaining unapplied cash. All allocations commit together; stale, duplicate-invoice, over-allocation and unauthorized requests change nothing.
- `POST /api/plinth/jobs/:job/remittances/:id/return`: `returned_on`, bank-return `reference`, `reason` and `confirm: true` record a full external return once. The date cannot precede receipt or allocation. Original evidence and allocations remain; negative receipt entries identify the originals they reverse, invoice balances reopen and any unapplied portion is retired. This records a bank/check return; it does not initiate a refund. Deposit requests and legacy single-invoice receipts retain their existing ledger; this door does not return them.
- `POST /api/plinth/jobs/:job/invoices/:invoice/return-receipt`: `receipt_id`, `returned_on`, bank-return `reference`, private `reason` and `confirm: true` reverse all or part of one directly recorded bank/check receipt. Optional `amount_cents` is positive integer USD cents no greater than the original amount minus all earlier returns; omit it to return only the remaining amount. A deposit return also needs enough current unapplied deposit liability for the requested amount. Each return reference must be unique case-insensitively against receipt and return evidence on this job; retrying it with a fresh job version still creates no second reversal. The date cannot precede the original receipt. A negative entry links the immutable positive original and a human approval retains both entries and the reason. Replayed evidence, over-returns, reversing a reversal, remittance-sourced receipts and returns consuming already-applied deposit funds are refused without writes. Use the remittance return door for remittance receipts. This records an external return and never initiates a refund or changes issued invoice terms or existing deposit applications.
- `GET /api/plinth/jobs/:job/receivables?as_of=YYYY-MM-DD`: current invoice balances, staff-recorded remittances and evidence, unapplied cash and milestone aging. The default date is today in the job zone. Due dates are inclusive; overdue buckets are 1–30, 31–60, 61–90 and 91+ calendar days. Unreleased retainage is separate from payable balances; deposit requests are listed separately and excluded from earned milestone aging. `as_of` changes age only, not current balances. This office report is not a historical cash statement.

Remittances appear as `remittance` financial records in RPT-004 scoped reports and exports, with native stages `recorded` and `returned`. Owners/administrators may supply `custom_fields` as a field-ID/value object in remittance actions; required fields are checked in the same transaction. Other users retain their existing custom-field rights. Use the financial values door for later changes. Native record amount is the original remittance amount; filter its native status when distinguishing recorded and returned entries. Unapplied cash and net invoice receipt balances come from the receivables report.

BILL-006 remains partial: provider reconciliation, partial remittance returns and returns consuming allocated deposit liability, disputed balances, collection ownership and receipt delivery/interface are unbuilt. Native bank/check evidence and browser navigation never establish provider settlement.

## Scoped checklist work

Signed-in people use `GET /api/plinth/todos?mine=true` for My to-dos and `/api/plinth/jobs/:job/todos` for granted job work. Owners/admins create company records; assigned project managers create job records. Every checklist item names a currently granted office, client or released subcontract contact. External people receive only the title and their own items, and no original attachments or office notes.

A completion, reopening or comment posts to `/:todo/{complete,reopen,comment}` with `expected_revision`, an `operation_id` and optional `item_id`. Offline web completions keep their original operation id and revision; stale work requires explicit review. A replay cannot change the recorded person or items. The native apps of FIELD-003 are not implemented by this web queue.

Owners/admins save reusable templates at `/api/plinth/todos/templates` and bind them to an actual schedule-template revision at `/api/plinth/todos/job-templates/:template`. Existing schedule preview/apply and quote acceptance create bound checklists atomically with their schedule. Current assignee grants are checked again, and reapplication preserves checklist state.

`/api/plinth/todos/preferences` records the current person's email choices. Prepared assignment/comment/reminder notices do not assert delivery. Only the owner explicitly approves a named email attempt at `/:todo/notices/:notice/send` with `channel`, `email` and `confirm`. Each durable attempt is reserved before the configured mail transport; unknown/refused/development outcomes are distinct and never automatically retried. Other channels and Buildertrend export ingestion remain unavailable as TODO-001's Gap records.

## Reviewed bid comparison and award

In a job's Bids tab, owners/admins prepare a comparison from two or more responses to the same current plan revision. Assigned project managers can read it. Interpret quantities, units, allowances, tax, exclusions, alternates, duration and missing scope against an exact original attachment or price line; recorded normalizations retain each review and never edit a vendor's response.

`GET /api/plinth/bid-comparisons/:job` returns original snapshots, reviews, commitments and the internal cost-plan overlay. `POST` with `package_id`, `title` and `expected_version` prepares a comparison. `POST .../:comparison/review` supplies the exact `candidate_id`/`response_id`, reviewed lines and original evidence references, exclusions, alternates, duration, rationale and `confirm:true`. Each line records its original quantity/unit (or explicitly not stated), allowance/tax, included/missing/unclear assessment and normalized cents.

`.../:comparison/award` approves the exact original response amount, current review, scope, dated terms reference, decision and the reviewed existing budget allocation being replaced for each code. It creates one subcontract commitment and source-keyed cost adjustment in the same version-checked transaction. Normalized comparison totals do not change vendor prices; frozen selling and billing budgets remain intact. Unknown original code costs block award until costed economics exist.

A repeated award is refused. `.../:comparison/replace` explicitly names `replaces_award_id` and a cancellation reason; `.../:comparison/cancel` names the exact award/subcontract and reason. Both preserve original award evidence and append the reversing cost adjustment. Released work or any orders, draws or retainage block this unstarted-work cancellation flow. No action sends money, notices or releases work. Clients, trade contacts and bearer agents cannot retrieve comparison records. Bid inbox access remains separate from award decisions: BID-001 supports explicitly invited, qualified contacts through either their own released scope or the conservative bid-only pre-award exception documented below.

## External portal grants and records

All of these are authenticated native Plinth HTTP doors. Use your ordinary signed-in session and matching `Origin` on writes. A bearer agent cannot submit portal records, set permissions or gain an external identity. Responses are private and never cached.

The owner changes a job's external feature restrictions with `POST /api/plinth/jobs/:job/portal-policy`, supplying its latest `expected_version`, a human-readable `reason`, and `disabled: {client: [], subcontractor: []}`. Lists name features to hide, not grants to create. Client features are `contracts`, `selections`, `changes`, `schedule`, `photos`, `billing`, `todos`, `handover`, `punch`, `rfis`, `warranty`; subcontractor features are `bids`, `schedule`, `todos`, `punch`, `rfis`, `bills`, `compliance`, `warranty`. An empty list retains existing record grants. Unsupported names, non-owner writers and stale versions are refused. Each change retains its actor, time, reason and prior/new lists in job history. These are per-job external restrictions; installation-wide/custom-role presets remain ROLE-006 work.

`GET /api/plinth/subcontractor-portal` lists a member's current qualified company awards. `GET /api/plinth/subcontractor-portal/:job` reads those scopes, current compliance requests and that company's own submitted bill/compliance originals. The same projection is searched with `?q=...`, exported at `/export.json` and downloaded at `/files/:file`. Current directory contacts and explicit award contact assignments are checked on every request. Work release is required for bills; an awarded scope on hold can supply evidence to resolve compliance. No general job, private rates, W-9 or other company's contacts/bills are exposed. Under the adopted conservative default, a current client on a job cannot also use a subcontractor directory contact on that same job to gain private company or bid access. Owner/admin and assigned project managers review intake through `GET /api/plinth/jobs/:job/subcontractor-portal` and its search/export/file suffixes.

A subcontractor posts `/api/plinth/subcontractor-portal/:job/bills` with `expected_version`, its own `subcontract_id`, a company bill `reference` unique within this job, `note`, positive integer `amount_cents` in USD and `attachments: [{name, base64}]`. PDF, PNG and JPEG originals retain their exact bytes and checksum. A bill is received only: no matching, approval, payable or payment is claimed. COST-002 and PAY-003 own those later decisions. A repeat company bill reference is refused rather than duplicated.

For `/api/plinth/subcontractor-portal/:job/compliance`, use the same fields except amount, exactly one attachment, plus `kind`, `issuer`, `effective_on`, `expires_on` and optional `limit_cents`/`endorsements`. Supported kinds are `general_liability`, `workers_comp`, `auto_liability`, `umbrella`, `license`. `verified` is refused. The existing owner/designated-reviewer compliance door receives the original as unverified evidence; the submission never clears a hold by itself. Company compliance evidence retains its company custody when a job is erased; job-local submissions and their attachment copies follow ordinary job erasure and private archives.

For a bid-only invitation before award, owner/admin posts the existing `/api/plinth/bids/:job/:package/invite` with `expected_version`, `vendor_id`, `contact_id`, selected `cost_codes`, `confirm: true` and `pre_award: true`, omitting `subcontract_id`. A current qualified company contact with an active member account is required. Without `pre_award`, the original own-released-scope rule still applies. A pre-award invitation creates no subcontract, grants no general job/work inbox and sends no notice. This implemented conservative exception remains partial pending ct confirmation of the cited ruling's exact changes.

The **Subcontractor records** navigation entry provides scoped bill/compliance originals, current review status, search and exports. Office users review submissions under **Purchasing**. The owner uses **History → External portal features** to change this job’s external restrictions. These screens use the same grants as their JSON doors, and a current review decision exposes no internal reviewer notes. Existing bid, selection, punch, RFI, trade and to-do screens obey the same feature checks. Copyable internal roles remain unfinished under ROLE-006.

## One-revision client signing delegation (CLIENT-006, partial)

Assigned clients keep the ordinary selection signing and dispute doors. A separate native HTTP workflow lets an assigned client delegate only one current presented revision to an existing eligible contact on that job's linked customer. It grants no job or customer-directory access. Dedicated client and delegate screens still await design authorization.

The client reads `GET /api/plinth/jobs/:job/selections/:selection/delegations` for eligible contact IDs/display names and retained delegation history. Posting to that path requires `expected_version`, the exact `revision_id`, an eligible `contact_id`, an attributed `statement` and `confirm: true`. Owners, administrators, project managers, agents and unrelated contacts cannot create one. A client or company contact on the job cannot be the delegate; the chosen contact must already have an active native member account. At most one unused live delegation exists per revision. No invitation or notice is sent.

The named delegate signs in normally and reads `GET /api/plinth/selection-delegations` or `/api/plinth/selection-delegations/:job/:delegation`. Only their own exact revision's client-visible terms, delegating statement and, after use, signature are returned. `POST .../:job/:delegation/sign` takes the current `expected_version`, exact `revision_id`, `option_id`, an affirmative `statement` and `confirm: true`. Every request rechecks both identities, current client and customer grants, company exclusion, feature availability and the exact revision. A new revision or substitute, dispute, withdrawal, disabled selections or lost signing authority voids an unused grant. Re-enabling access does not revive a voided grant. Concurrent client/delegate signatures commit one immutable choice.

Any assigned client revokes an unused grant at `POST /api/plinth/jobs/:job/selections/:selection/delegations/:delegation/revoke` with `expected_version` and a reason. Revoking after use is refused and retains the signature; clients use the existing dispute door. The delegation, revocation and signature provenance appear in office and assigned-client History, survive private archive restore, and disappear on job erasure. A delegated choice alone changes no finances; allowance variations still require assigned-client approval. No comment, dispute, withdrawal, variation or other signature authority passes to the delegate.


## Source-backed cost billing (BILL-004, partial)

An office administrator with existing cost access can prepare a cost-plus draft through `POST /api/plinth/jobs/:job/invoices`. Send the current `expected_version`, `kind: "cost_plus"`, the normal description, authorized recipient email, due date and terms, plus `cost_billing` containing:

- `contract_reference`: the reviewed signed agreement reference.
- `entry_ids`: posted actual-cost entry ids selected from the existing job cost ledger. Draft costs cannot be billed.
- `fee_bps`: the fixed contractual fee, in basis points. The net selected cost times this rate rounds half-up once to integer cents.
- `cap_cents`: the cumulative gross cap; the draft separately shows any reduction needed to stay within it and the accepted contract total still limits issue.
- `excluded_entry_ids`: posted costs excluded by the agreement. Once recorded on an issued invoice, these sources cannot be selected on a later issue.

The returned draft is the preview; its `sources.cost_billing` includes source entries, supporting time details and original receipt checksums, fee, cap reduction and prior invoice links. Supporting records remain under existing office cost custody; clients receive invoice selling lines without private time details or receipt snapshots. Current preparation requires a reviewed zero sales tax agreement. Taxable pricing, category-specific fees, standalone net credits and the cost selection form remain unfinished.

Approve the draft through the existing Billing record or `POST /api/plinth/jobs/:job/invoices/:invoice/issue` with a fresh `expected_version`. Issue rechecks current sources and earlier allocations atomically. A competing draft cannot rebill a source. The issued reference, fee and cap are fixed for later batches. A later positive net batch can combine approved late time and a posted vendor credit; it links the earlier issues without changing their originals. Download the issued original using the existing invoice document commands. Cost billing and progress applications cannot share earned billing on the same job. No mail or funds move as a consequence of prepare or issue.

## Native meeting and decision HTTP doors

The installed Meetings and Decision search sections use authenticated HTTP. CT approved the private-office defaults on 26 October 2026: raw meetings stay private to current owners, administrators and assigned project managers; attendance and copied custom roles grant no implicit access. Clients search only their currently permitted records and correspondence. Agents cannot record meetings or search decisions.

Relative to the job endpoint, `POST /meetings` takes the current `expected_version`, `title`, `held_on`, `agenda`, `minutes`, `attendees`, `decisions`, optional `tags`, `sheet` and `cost_code`, and an `actions` list. Each action has `title`, an active office `owner_email` who currently manages the job, and `due_on`. Dates are calendar dates in YYYY-MM-DD form. Meetings are append-only records; each job supports up to 200 meetings and each meeting up to 50 actions.

`POST /meetings/:meeting/add-action` adds another assigned action with the current job version.
