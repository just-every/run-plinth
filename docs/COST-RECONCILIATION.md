# Pre-draw cost reconciliation

The signed-in owner can request a private native diagnostic before preparing a draw. It preserves suspected duplicate originals, unposted native labor, draft bill coding and receipt discrepancies as evidence. It does not change a bill, cost entry, forecast, pay application, payroll, payment or exception decision.

Use the job's `./api/plinth/jobs/:id/cost-reconciliation` HTTP collection. A POST requires the current `expected_version`, an `as_of` date and a reason. A GET returns the immutable packet history with current source freshness and whether owner review is required.

Each finding retains exact native identities and original checksums where an original exists. Duplicate candidates compare original bytes across distinct bill references, including posted originals, and remain suspicions. Receipt quantities are recorded observations. Native bill lines contain monetary amounts rather than attested billed quantities, so the diagnostic reports that physical comparison as unknown. Labor candidates omit individual pay rates and employee details. Findings overlap; adding them together would double count exposure.

To authorize a draft agent request, POST to the packet's `review` action with its digest, current job version, `confirm: true`, explicit `finding_ids` and a review reason. The `plinth.costs.packets` tool lists only current reviewed packet identities. The `plinth.costs.reconcile` tool takes a job identity, packet identity and exact digest through the existing MCP policy door. It consumes only selected findings and appends a proposed coding, matching or correction packet. MCP returns a content-free receipt; the signed-in owner inspects the full proposal and exact evidence through the native packet history. Shared agent caches therefore retain no private cost evidence. Source changes, withdrawal, a revoked credential or erasure prevent another execution and prevent replay from returning the former packet contents.

The owner can record an `accepted` or `rejected` suggestion using the packet's `decide` action, supplying the proposal and finding identities, digest, current version and reason. Both decisions remain in history. Acceptance records a decision about the suggestion; it does not approve a cost. Use the original human bill review, source approval, coding, credit, payroll and exception doors for any actual correction. Existing separation and accounting-period rules still apply. Request a new diagnostic after source changes.

A packet's `revoke` action withdraws its consent permanently. Recovery preserves its evidence and rejected suggestions, while the receiving installation requires fresh owner review because authentication generation changes on restore. No provider credentials or standing consent travel with this history.

Live accounting and payroll reconciliation, the complete maintained agent across those sources and provider-backed staff follow-through remain unfinished AGENT-005 obligations. No live synchronization, professional certification, delivery, funds movement or payroll execution is claimed.

## Human quantity evidence and correction follow-through

The `quantity-evidence` collection under the reconciliation door records supplementary observations, preserving all native receipt quantities and original bill bytes. The signed-in owner records a `bill_read` against an exact bill line, original checksum, order line and explicitly matched receipt. An assigned superintendent records a `field_receipt` quantity against that same receipt and order line. Crew can read the field projection; it omits private bill identities, amounts and office readings. An agent cannot record either kind.

Each observation supplies its exact native identities, `quantity`, the original order `unit`, `dated_on`, a human evidence reference and `supersedes`. Use null for a first observation and the current observation identity for a correction. Earlier readings remain in history. There is no implicit unit conversion. Job versions and current assignment are checked on every write. A later observation invalidates earlier reviewed agent packets. A fresh diagnostic compares the bill reading, original receipt and latest field attestation; missing evidence remains unknown. These are attributed human observations, never independent certification of physical completion.

After accepting a suggestion and completing its correction through the existing human door, the owner can POST to the packet's `outcome` action with the proposal and finding identities, exact packet digest, current version, `correction_id` and reason. The server verifies the exact native approved source and its ledger entries, a posted bill or credit and its original link, or a superseding quantity observation whose current readings agree. An unposted source, unrelated correction, rejected suggestion or repeated outcome is refused. The old diagnostic can record this outcome after its sources change; it still cannot authorize another agent preparation. Outcomes retain native record identities and never execute the correction, certify a provider result or clear an exception. Prepare the next native forecast or draw separately to inspect the approved inputs.
